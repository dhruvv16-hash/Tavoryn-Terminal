## 1. Executive Summary & Security Posture

Tavoryn Terminal Research Edition v1.0 is engineered with an **offline-first, zero-runtime-dependency, local-by-design** architecture. Because the terminal operates locally on the analyst's machine rather than in a multi-tenant cloud environment, its security perimeter is designed to prevent cross-site hijacking, local directory traversal, unauthorized process manipulation, and unintended capital deployment.

### Core Security Tenets
1. **Zero External Runtime Dependencies:** The production server requires zero third-party npm packages (`"dependencies": {}` in `package.json`), completely eliminating supply chain attacks, package typosquatting, and malicious transitive dependencies.
2. **Local Machine Binding:** Default HTTP listener binds strictly to `127.0.0.1` (`HOST || '127.0.0.1'`).
3. **Cross-Site Hijacking Resistance (CSRF/Origin Defense):** All state-mutating HTTP methods (`POST`, `PUT`, `PATCH`, `DELETE`) require custom client headers and strictly validated origins.
4. **Capital Safety & Broker Isolation:** Live capital execution routes are strictly disabled and fenced off. Built-in trading is restricted to isolated paper accounts.
5. **Atomic Storage & Data Quarantine:** All local persistence uses atomic temporary file writes and directory bounds enforcement.

## 2. Threat Modeling & Perimeter Defenses

### A. Host Header & Origin Enforcement
To prevent DNS rebinding attacks and cross-origin exploitation from malicious websites running in the user's browser, `server.js` implements deterministic perimeter filtering in `allowed(req)`:

```javascript
// server.js lines 83-101
function allowed(req) {
  const host = (req.headers.host || "").replace(/:\d+$/, "").replace(/^\[|\]$/g, "");
  const okHosts = new Set(["localhost", "127.0.0.1", "::1", ...lanAddresses()]);
  if (!okHosts.has(host)) return false;
  
  if (req.method !== "GET" && req.method !== "HEAD") {
    // 1. Enforce custom application header (cannot be added cross-origin by arbitrary forms)
    if (req.headers["x-qt"] !== "1") return false;
    
    // 2. Enforce strict origin matching
    const origin = req.headers.origin;
    if (origin) {
      try {
        if (new URL(origin).host !== req.headers.host) return false;
      } catch {
        return false; // Rejects "null" and opaque browser origins
      }
    }
  }
  return true;
}
```

#### Security Validation & Proof
- **Attack Vector:** An attacker hosts an evil webpage that triggers `fetch('http://localhost:3787/api/shutdown', { method: 'POST' })`.
- **Defense Result:** Request is blocked with `403 Forbidden` because standard cross-origin requests cannot set custom headers like `x-qt: 1` without pre-flight approval, and the browser attaches `Origin: http://evil.com` which fails the host comparison.
- **Automated Test:** Verified in `test/server.test.js`:
  - `✔ writes without the app header are refused (15.39ms)`
  - `✔ an opaque Origin is refused with 403, not a crash (15.65ms)`

### B. Directory Traversal Resistance
The static file delivery engine (`serveStatic`) serves client files from `public/` and custom scripts from `custom/`. To guarantee that an attacker cannot escape the designated directories via path traversal (`../../etc/passwd` or `..\..\Windows\win.ini`), path resolution is strictly bounded:

```javascript
// server.js lines 111-124
function serveStatic(res, baseDir, rel) {
  const file = path.normalize(path.join(baseDir, rel));
  if (!file.startsWith(baseDir + path.sep)) return send(res, 403, "Forbidden");
  fs.stat(file, (err, st) => {
    if (err || !st.isFile()) return send(res, 404, "Not found");
    // Serve file stream
  });
}
```

#### Endpoint Function Routing Sanitization
Dynamic function dispatching (`/api/fn/<name>`) strictly validates requested function identifiers against an alphanumeric regular expression before attempting disk operations:
```javascript
// server.js line 459
const fm = /^\/api\/fn\/([a-z0-9-]{1,40})$/.exec(p);
```
This guarantees that path delimiters (`/`, `\`, `.`) cannot be injected into dynamic module imports.
- **Automated Test:** Verified in `test/server.test.js`:
  - `✔ static files cannot escape their folder (59.88ms)`
  - `✔ symbols that could reshape an upstream URL are refused (169.89ms)`

## 3. State & Accounting Integrity

### A. Atomic File Writes & Windows Lock Resilience
Local workspace state, watchlists, drawing annotations, and paper account ledgers are stored as JSON documents in `data/`. Incomplete writes due to sudden process crashes or power interruptions are prevented via two-phase atomic writes in `lib/store.js`:

1. **Phase 1 (Temp Write):** Data is serialized and written to `${file}.${process.pid}.tmp`.
2. **Phase 2 (Atomic Rename):** Node.js executes `fs.renameSync(tmp, file)`.
3. **Phase 3 (OS Lock Fallback):** On Windows, file indexers or antivirus scanners may momentarily lock open files, returning `EPERM`, `EBUSY`, or `EACCES`. Rather than dropping analyst state, the system catches these codes, performs a safe direct write, and unlinks the temporary file.

### B. Paper Account Ledger Protection & Quarantine
The paper trading ledger (`data/paper-account.json`) represents simulated account capital. To protect against file corruption:
- If `JSON.parse` fails on startup, the corrupted file is automatically quarantined to `data/paper-account.corrupted.<timestamp>.json` rather than overwritten, preserving forensic data.
- Execution ordering is serialized through a sequential promise queue (`runLocked` in `lib/paper-trading.js`). Concurrent orders cannot race on cash balances or position allocations.
- Balance check: Cash cannot drop below zero (`cash - reservedCash >= orderCost`).
- Position closing: Short and long position liquidation is tracked against real open positions; closing quantities exceeding open positions are rejected.

## 4. Capital Safety Fencing & Broker Isolation

### A. Phase 10 / Live Trading Freeze
In accordance with institutional safety policies, **live broker execution is disabled in Tavoryn Terminal Research Edition v1.0**.

| Component | Policy | Active Implementation |
| :--- | :--- | :--- |
| **Broker Gateways** | Live Orders Permitted = `false` | `server.js` (`/api/market-data/health`) reports `brokerIsolation: { isLiveBrokerConnected: false, liveOrdersPermitted: false }` |
| **API Keys / Credentials** | No Live Secret Storage | No broker credentials (e.g. Alpaca, IBKR) are stored or loaded in environment or config files |
| **PTQ Integration** | Read & Fail-Safe Only | `/api/ptq/*` endpoints permit status reading, checks, and emergency kill-switches only. Order arming is forbidden over HTTP. |
| **Mock Broker** | Test-Only Isolation | `lib/broker/mock-broker.js` is instantiated exclusively inside automated tests (`test/phase7-broker-integration.test.js`). |

### B. Pre-Trade Risk Gateway
Before any simulated order touches the execution engine, it passes through `PreTradeRiskGateway` (`lib/broker/risk-gateway.js`), which enforces 16 deterministic risk controls:
1. `KILL_SWITCH_ACTIVE`: Immediate block if kill-switch is engaged.
2. `INVALID_ORDER_SPEC`: Validates ticker, quantity, price, and side.
3. `DISALLOWED_INSTRUMENT`: Rejects unapproved asset classes.
4. `DISALLOWED_ORDER_TYPE`: Allows only `MARKET`, `LIMIT`, `STOP`, `STOP_LIMIT`.
5. `STALE_OR_DEGRADED_FEED`: Rejects trades if market data is older than `feedMaxAgeMs` (15,000 ms).
6. `MAX_ORDER_QTY_EXCEEDED`: Hard limit on single order contracts/shares.
7. `MAX_ORDER_NOTIONAL_EXCEEDED`: Dollar cap per order.
8. `RATE_LIMIT_EXCEEDED`: Maximum order submissions per minute (default 60/min).
9. `MAX_OPEN_ORDERS_EXCEEDED`: Prevents runaway algorithmic order spam.
10. `DAILY_LOSS_LIMIT_REACHED`: Halts trading if intraday losses exceed threshold.
11. `INSUFFICIENT_BUYING_POWER`: Verifies cash backing before submission.
12. `MAX_POSITION_EXPOSURE_EXCEEDED`: Limits single-asset portfolio concentration.

## 5. Process Reliability & Clean Recovery

### A. Port Conflict Hunting
If port 3787 is already bound by another application or an existing terminal instance, `server.js` automatically increments the port and attempts up to 20 successive ports (3787–3807), logging the active URL to stdout.

### B. Graceful Shutdown & Lifecycle Management
- **Controlled Local Termination:** The server exposes `POST /api/shutdown` requiring the `x-qt: 1` header. This endpoint allows automated management scripts (`scripts/stop.js`) and update installers to cleanly flush state and terminate the server.
- **Process Signals:** Handlers for `SIGINT` (Ctrl+C) and `SIGTERM` ensure open file descriptors are closed and logs are flushed before exiting.
- **Background Daemon:** `scripts/launch.js` and `scripts/stop.js` provide background process supervision without requiring PM2 or external process managers.
